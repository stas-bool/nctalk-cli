# Заметки по реализации 2026-10-09-nctalk-chat-attach-design.plan.md

## Решения

## [Task 1] Доп. пробы WebDAV после расхождения PUT: MKCOL без родителя — 409, HEAD в отсутствующей папке — 404
Что: сверх протокола брифа сделаны три запроса, которые ничего не создают: MKCOL `/<нет такой папки>/a` → 409 `Sabre\DAV\Exception\Conflict` «Parent node does not exist», родитель не создан (HEAD 404); HEAD файла внутри отсутствующей папки и HEAD самой папки → 404. Пункт §3.4 «MKCOL … прочее → ошибка (в т.ч. 409 — нет родителя у вложенной папки)» и кейс `MKCOL 409 (нет родителя)` в `TestSendFile_MissingFolder` верны и не меняются; в `uploadFile` цепочка «нет папки» на живом сервере — HEAD 404 (имя свободно) → PUT 404 → MKCOL → PUT.
Почему: голый Sabre на PUT без папки отвечает 409, а живой сервер — 404 (см. «Отклонения»). Без проб нельзя было сказать, расходятся ли так же MKCOL и HEAD, — от этого зависят кейсы теста и порядок шагов в адаптации Task 4. Мутаций на боевом пробы не добавили.

## Отклонения

## [Task 1] PUT в несуществующую папку — 404 NotFound, не 409 (строка 4 таблицы Step 9)
Что: живой сервер (NC 34.0.3) на `PUT` с `If-None-Match: *` в отсутствующую папку отвечает HTTP 404 `Sabre\DAV\Exception\NotFound` «File with name /<папка> could not be located», а не 409 `Conflict` «Files cannot be created in non-existent collections», как ждали бриф и спека §3.4. По строке 4 `testdata/dav_error_409.xml` — тело этого 404: имя файла прежнее, внутри `NotFound` и `s:message` «File with name /nctalk-fixture-missing could not be located». Остальные статусы WebDAV совпали с ожидаемыми: PUT поверх существующего — 412, HEAD существующего/отсутствующего — 200/404, MKCOL существующей папки — 405. Спека поправлена с пометкой «(уточнено по живому API 2026-10-09)»: §3.4 (PUT 404 или 409 → MKCOL и один повтор), §2.6 (404 в списке ошибок WebDAV, exit `1`), §7 (фикстура «PUT без папки» и кейс «нет папки» в тестах client), §8 (CLAUDE.md: «MKCOL по 404/409»).
Почему: живой API — истина. Код плана на 404 вернул бы ошибку `PUT …: HTTP 404` вместо MKCOL, и при отсутствующей папке вложений (классический путь её не создаёт, §1) файл не отправился бы вовсе.
Последствие: Task 4 адаптирует код плана. (1) `davPut`: `http.StatusNotFound` — в список статусов, возвращаемых вызывающему (201/204/404/409/412). (2) `uploadFile`: MKCOL и один повтор при `status == http.StatusNotFound || status == http.StatusConflict`; 404/409 после MKCOL — прежняя ошибка «папка вложений %s недоступна (PUT: HTTP %d)»; DAV-404 не превращать в `*OCSError{404}`: это exit `1`, а не `2`. (3) `fakeNC.handleDAV`, ветка PUT: тело `dav_error_409.xml` отдавать и при 404, и при 409. (4) `TestSendFile_MissingFolder`: добавить кейсы `{"404 → MKCOL 201 → PUT 201", []int{404, 201}, 201, ""}` и `{"PUT 404 после MKCOL", []int{404, 404}, 201, "папка вложений /Talk недоступна (PUT: HTTP 404)"}`; 409-кейсы оставить (голый Sabre). Комментарии «409 — нет папки» → «404/409». Task 2 — по желанию, на поведение не влияет: в `TestDoDAV_SabreMessage` кейс «409 живой» переименовать в «404 живой (PUT без папки)» со статусом `http.StatusNotFound`; тест проходит и без этого, `s:message` он берёт из фикстуры. Task 7 — в блоке CLAUDE.md «MKCOL по 409» → «MKCOL по 404/409».

## [Task 2] Адаптация кейса по живому API: 404 вместо 409
Что: после уточнения Task 1 о живом API (сервер на PUT без папки отвечает 404, не 409) в `TestDoDAV_SabreMessage` переименован кейс с `{"409 живой", http.StatusConflict, …}` на `{"404 живой (PUT без папки)", http.StatusNotFound, …}` и обновлен doc-комментарий теста: фраза «(Task 1: 409 PUT без папки, 412 If-None-Match на существующий файл)» → «(Task 1: 404 PUT без папки — живой сервер отвечает 404, не 409; 412 If-None-Match на существующий файл)».
Почему: живая фикстура `dav_error_409.xml` содержит XML-ошибку с `<s:message>` для HTTP 404 (не 409), поэтому тестовый кейс должен отражать реальный статус. Бриф Step 1 давал код с `http.StatusConflict`, но адаптация Task 1 уточнила, что на живом API сервер отвечает 404.
Последствие: тест по-прежнему проходит, т.к. код извлекает `s:message` из фикстуры независимо от статуса; самопроверка в конце теста (`fixtureSabreMessage(t, davFixture(t, "dav_error_412.xml")) == ""`) гарантирует, что фикстуры содержат текст `<s:message>`.

## [Task 4] SendFile: PUT без папки вложений — 404 (MKCOL по 404/409); DAV-404 остаётся обычной ошибкой
Что: код брифа Task 4 внесён с правками по записи Task 1 (живой сервер на PUT в отсутствующую папку отвечает 404, а не 409). (1) `davPut`: `http.StatusNotFound` добавлен к статусам, которые возвращаются вызывающему, — теперь 201/204/404/409/412 (решение плана №12 расширено на 404). (2) `uploadFile`: MKCOL и один повтор PUT при `status == http.StatusNotFound || status == http.StatusConflict`; 404/409 после MKCOL — прежняя ошибка «папка вложений %s недоступна (PUT: HTTP %d)»; DAV-404 в `*OCSError{404}` не превращается. (3) `fakeNC.handleDAV`: на PUT со статусом 404 и 409 отдаётся одно тело `testdata/dav_error_409.xml` (имя прежнее, внутри живой 404 NotFound). (4) `TestSendFile_MissingFolder`: два новых кейса — `404 → MKCOL 201 → PUT 201` и `PUT 404 после MKCOL`, подтестов стало 6, 409-кейсы оставлены (голый Sabre); в ветке ошибки добавлена проверка, что ошибка загрузки — не `*OCSError`. Комментарии «нет папки → 409» в `FileUpload`, `SendFile`, `uploadFile`, `davPut` переписаны на «404/409».
Почему: код брифа на 404 вернул бы ошибку `PUT …: HTTP 404` вместо MKCOL, и при отсутствующей папке вложений (классический путь её не создаёт, §1) файл не отправился бы вовсе. Проверка «не `*OCSError`» нужна потому, что в cli любой `*OCSError{404}` из клиента даёт exit 2 (`exitFromClientErr`), а ошибки WebDAV по контракту — exit 1 (§2.6).
Последствие: на живом сервере цепочка «нет папки» — HEAD 404 → PUT 404 → MKCOL → PUT 201. Новые проверки проверены мутациями в копии репозитория: без `StatusNotFound` в `davPut` падают оба 404-кейса; DAV-404, превращённый в `*OCSError{404}`, ловит новая проверка. Task 5 (cli) может исходить из того, что `*OCSError{404}` из `SendFile` приходит только от OCS-шагов (pre-check треда и сообщения, шаринг), а DAV-404 — обычная ошибка (exit 1). См. запись «[Task 1] PUT в несуществующую папку — 404 NotFound, не 409» выше.

Что: в блоке «Вложения» CLAUDE.md фраза брифа «Классический путь папку вложений НЕ создаёт — MKCOL по 409, один раз.» заменена на «… MKCOL по 404/409 (живой сервер на PUT без папки отвечает 404, голый Sabre — 409), один раз; DAV-404 — ошибка WebDAV (exit `1`), не OCS 404.» Остальной текст блока — дословно по брифу; «повтор после 409/412 упал бы» (про `io.NopCloser`) не трогали: утверждение верно и без 404.

Последствие: CLAUDE.md теперь совпадает с `uploadFile` (MKCOL и один повтор PUT при 404 или 409; 404/409 после MKCOL — ошибка «папка вложений … недоступна», exit `1`) и с §2.6/§3.4 спеки в редакции «уточнено по живому API 2026-10-09». ## [code-review] DoDAV: отрицательный contentLength — ошибка до сети; при 0 тело не читается
Что: по замечанию M-1 code-review (2026-10-10) в `transport.DoDAV` добавлен guard: `contentLength < 0` → ошибка «transport: DoDAV: отрицательная длина тела N …» до сборки запроса, сервер не получает ни одного запроса. Регресс-тест `TestDoDAV_NegativeContentLength`; red — при -1 и -5 тело уходило chunked и сервер отвечал 201. Ветка `contentLength == 0` механику не меняет: doc-комментарий `DoDAV` и спека §4.1 теперь прямо говорят, что при 0 тело не читается и уходит `http.NoBody`. Спека §4.1 поправлена с пометкой «(уточнено по code-review 2026-10-10)».
Почему: у net/http отрицательная длина значит «неизвестна», и Go молча шлёт тело chunked. Проверено: при -1 и -5 сервер видит `Transfer-Encoding: chunked`, клиент получает 201. А за php-fpm chunked-тело в части конфигураций приходит пустым, и сервер создал бы пустой файл с 201. Сейчас путь недостижим (`validateSendFile` отсекает `Size < 0`), но `DoDAV` задуман транспортом и для будущих `files ls/get/find`, а -1 — привычное в Go «длина неизвестна». Вариант ревьюера «`contentLength == 0 && body != nil` → ошибка» отклонён, ревьюер в follow-up согласился: так передаётся пустой файл (`*os.File`, `Size 0`) — штатный путь §2.3 (`TestSendFile_EmptyFile`), а отличить пустое тело от непустого без чтения нельзя.

## [code-review] cli: повторный Stat не закрывает подмену на FIFO — комментарий и спека §2.3/§6 уточнены, механика прежняя
Что: по замечанию M-2 code-review (2026-10-10) уточнены комментарий `chatSendAttach` и спека §2.3/§6 (пометка «(уточнено по code-review 2026-10-10)»). Повторный `Stat` берёт тип и размер у открытого дескриптора и ловит подмену пути на не обычный файл, но FIFO без писателя, подложенный между `os.Stat` и `os.Open`, `open(2)` всё же заблокирует. Порядок `os.Stat` → `os.Open` → `Stat` и тесты не менялись.
Почему: прежний текст «повторный `Stat` закрывает подмену файла между проверкой и открытием» обещал больше, чем делает код. `O_NONBLOCK` отклонён. Снять флаг после проверки — unix-only код под build-тегами: `syscall.SetNonblock` на unix принимает `int`, на Windows — `Handle`. Если флаг оставить, `os.OpenFile` помечает файл как `kindNonBlock`, и рантайм Go на darwin кладёт обычный файл в kqueue в обход своей защиты (issue 19093). Платить за это пришлось бы на каждом вызове ради окна в микросекунды, которое создаёт только владелец пути. Исход гонки — зависание до Ctrl-C, без порчи данных.

## [code-review] DoDAV: тело — снимок первых contentLength байт, растущий файл больше не ломает загрузку
Что: по находке верификации code-review (2026-10-10, вне M-1…M-4) в ветке `default` у `transport.DoDAV` тело — `io.NopCloser(io.LimitReader(body, contentLength))` с явным `req.ContentLength`. Уходит ровно `contentLength` байт, снимок на момент `Stat`; хвост, дописанный после, не отправляется. Обёртка создаётся на каждый вызов, повтор PUT после 404/409/412 с `Seek(0)` работает как раньше (`TestDoDAV_BodyReusableAfterSend`, `TestSendFile_PutRetryRealFile` зелёные). Укоротившееся тело — по-прежнему ошибка транспорта net/http через `SanitizeErr`, без отдельной обработки. Регресс-тесты: `TestDoDAV_BodyLongerThanContentLength` (reader длиннее и растущий `*os.File`; red — `http: ContentLength=N with Body length M`, 10 из 10 прогонов) и `TestDoDAV_BodyShorterThanContentLength` (закрепляет ошибку для короткого тела). Спека §3.4/§4.1 и инвариант «Вложения» CLAUDE.md поправлены, пометка «(уточнено по code-review 2026-10-10)».
Почему: «скинь лог в чат» — основной сценарий (§1). Если файл растёт между `Stat` и концом загрузки, сервер получает ровно N байт и создаёт файл (201), а net/http, дочитав хвост, возвращает клиенту ошибку `ContentLength=N with Body length M`. Итог — exit `1` без шаринга и cleanup, файл-сирота в папке вложений, а повтор вызова даёт `name (2)`.
