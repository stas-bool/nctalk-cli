## 🔴 Блокер

### 1. TestChatThreadsSubstituteParams не сможет позеленеть: общий `*client.Message` мутируется текстовым вызовом

1. **Пункт:** Task 3, Step 1, тест `TestChatThreadsSubstituteParams` — блок «// JSON — БЕЗ подстановки.»: `deps2 := newChatDeps(&chatSpyClient{threadsResult: result})` переиспользует тот же слайс `result`, что и текстовый вызов выше.
2. **Что не так:** `ThreadInfo.First`/`Last` — указатели (`*client.Message`), а handler (Task 3 Step 5, шаг 6) делает подстановку in-place: `ts[i].First.Message = render.SubstituteParams(...)`. После первого (текстового) вызова оба шпиона смотрят на уже подставленные строки, поэтому JSON-вызов сериализует «Анна поделился файлом report.pdf», ассерт `strings.Contains(raw, "{actor} поделился файлом {file}")` ложен → `t.Errorf("JSON хранит оригинальный message")` срабатывает на ПРАВИЛЬНОЙ реализации. Красная фаза (Step 2) этого не видит (падение на компиляции `undefined: chatThreadsHandler`) — тест сломается только на зелёном прогоне Step 6, ломая TDD-цикл задачи. Пруф расхождения с существующим паттерном: у `chat show` мутации нет, потому что `filtered` в `chatShowHandler` (handlers_chat.go:177–191) — копии-значения `client.Message`, а тут элементы достаются через указатели.
3. **Что сделать:** для JSON-ветки собрать свежий литерал `result2` (или хелпер по образцу `makeThreadInfo`) со своими `First`/`Last`; не переиспользовать `result` между двумя шпионами.

## 🟡 Стоит уточнить

### 2. Task 1: фикстура `threads/recent` может нести чужие треды из общесетевой integration-комнаты

1. **Пункт:** Task 1, Step 1 п.3 (`curl ... "$API/threads/recent?limit=5"`) и Step 3 (скелет `testdata/threads_recent.json` с единственным элементом `data`).
2. **Что не так:** integration-комната (`NCTALK_INTEGRATION_ROOM`) используется многократно — там уже работают `TestIntegration_SendMessage`/`EditMessage` и будут прогоны самого `TestIntegration_Threads`; `threads/recent` вернёт до 5 последних тредов, среди которых свежесозданный — только первый. План нигде явно не говорит «оставить в `data` только элемент треда этого прогона, остальные удалить» — скелет это лишь подразумевает. Риск: в публичный репозиторий (`stas-bool/nctalk-cli`) попадут реальные названия/тексты/авторы чужих обсуждений, а контроль Step 4 их не поймает — grep проверяет только `nextcloud\.|https?://…`, не имена. Заодно фиксируется недетерминированность фикстуры.
3. **Что сделать:** в Step 3 добавить явное правило нормализации: в массиве `data` фикстуры `threads_recent.json` остаётся ТОЛЬКО тред текущего прогона (id 1234/1300), остальные элементы удаляются; при желании расширить grep Step 4 на проверку отсутствия «сырых» элементов (например, сверка `jq '.ocs.data | length' == 1`).

### 3. Task 6 Step 5: верификационный grep даёт ложное «пусто» для CLAUDE.md

1. **Пункт:** Task 6, Step 5: `grep -rn "9 команд\|9 методов\|9 примитивов" --include="*.go" --include="*.md" . ~/.claude/skills/nctalk/SKILL.md | grep -v "docs/superpowers"`; Expected: «пусто».
2. **Что не так:** фильтр `grep -v "docs/superpowers"` вырезает по СОДЕРЖИМОМУ строки, а не по пути. Строка CLAUDE.md:5 — единственное место в .md, где надо менять «9 команд», — сама содержит `docs/superpowers/specs/…` (перечень спек), т.е. если исполнитель забудет правку CLAUDE.md, остаточный hits будет молча отфильтрован и проверка выдаст ложное «пусто». Пруф: прогон точного пайплайна из плана на текущем дереве — `./CLAUDE.md:5` исчезает из выдачи именно из-за `grep -v docs/superpowers` (в полном выводе рекурсивного grep строка есть).
3. **Что сделать:** фильтровать по пути, а не по содержимому: `… | grep -v '^\./docs/superpowers/'` — или исключать каталог на этапе grep (`--exclude-dir=superpowers` у GNU/ugrep; для BSD grep — отдельный прогон без захода в docs/).

## 🟢 По красоте

### 4. Task 4 Step 1 п.4–5: неверные обоснования «иначе анти-drift упадёт»

1. **Пункт:** Task 4, Step 1: «`valueForFlag` — кейс для `--thread` (иначе анти-drift prong 1 упадёт на парсинге «x» как int…)» и «`buildPositionalArgs` — кейс (иначе prong-и анти-drift вырождаются на «укажите token»)».
2. **Что не так:** prong 1 (`TestAntiDrift_HandlerMatchesDeclaration`, help_test.go:505) ругается ТОЛЬКО на ошибки, содержащие «неизвестный флаг»; ошибка парсинга «--thread ожидает целое число, получено "x"» тест проходит, а prong-и 2/3 не требуют позиционных (scan флагов идёт до ResolveRoom и до «укажите token»). Оба дополнения — правильная гигиена (валидное значение и валидные позиционные), но не необходимые для зелёного прогона.
3. **Что сделать:** поправить формулировки («для честного валидного значения / консистентности», без «иначе упадёт»), чтобы исполнитель не тратил время на поиск несуществующей красной фазы.

### 5. Формат `ThreadsTable` расходится с образцом спеки §2.1 в разделителях

1. **Пункт:** Task 3, Step 4: `line := fmt.Sprintf("[%d] %s %s ⟲%d", …)` + `" " + threadLastPreview(...)` — одинарные пробелы.
2. **Что не так:** образец §2.1 спеки показывает двойные разделители: `[1234] 2026-09-29 14:02:05  Отчёт за сентябрь  ⟲5  Вася: цифры…` (при этом образец §2.4 совпадает с реализацией точно). Тесты используют `Contains`, так что поведенческого конфликта нет — но «эталон контракта» и вывод разойдутся зрительно.
3. **Что сделать:** осознанно выбрать один вариант: либо привести формат-строку к образцу §2.1, либо зафиксировать в §2.1 спеки одинарные пробелы (поправка спеки одной строкой).

### 6. TestListThreads_MessageParamsObject зависит от форматирования фикстуры

1. **Пункт:** Task 2, Step 1, `TestListThreads_MessageParamsObject`: `strings.Contains(s, "\"messageParameters\": {")`.
2. **Что не так:** проверка предполагает пробел после двоеточия (jq pretty-print по умолчанию); фикстура, записанная компактно (`"messageParameters":{`), даст ложное падение «ожидается объектный messageParameters» при корректном содержимом. Само наличие ключа сомнений не вызывает: живые chat-API ответы всегда несут `messageParameters` (в т.ч. пустой `{}` — см. `testdata/chat_edit_response.json`, parent).
3. **Что сделать:** сделать проверку нечувствительной к пробелам (например, regexp `"messageParameters":\s*\{` или `strings.Contains(s, "\"messageParameters\":{") || strings.Contains(s, "\"messageParameters\": {")`).
