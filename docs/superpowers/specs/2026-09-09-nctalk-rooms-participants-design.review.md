### 3. `--name` может разрезолвить former-комнату — сценарий не специфицирован, «на практике недостижимо» неточно

- **Цитата (§2):** «Пустой список участников → пустой stdout… (на практике недостижимо — сам
  запрашивающий всегда участник доступной ему комнаты)».
- **Что не так:** `ResolveRoom` ищет через `client.FindRooms`, который сознательно запрашивает
  список с `IncludeFormer: true` — «Поиск идёт по ВСЕМ комнатам, включая former (типы 4/5/6)»
  ([internal/client/rooms.go:80-84](file:///Users/stas/Projects/My/NCCliClient/internal/client/rooms.go),
  вызов из `internal/room/room.go:96`). Значит `rooms participants --name "<имя покинутой
  комнаты>"` может разрезолвить комнату, которую пользователь ПОКИНУЛ: он там не участник,
  «сам запрашивающий всегда участник» ложен для этого пути. Поведение `GET …/participants`
  на такой комнате спекой не определено (404 → exit 2? 200 без запрашивающего?) — контракт
  exit-кодов покроет любой исход, но наблюдение «недостижимо» и семантика для former не
  описаны. Интеграционный тест это не поймает: он берёт первую комнату `ListRooms` с дефолтными
  opts (former исключены).
- **Что сделать:** либо явно в Out of scope с формулировкой «former-комната через --name →
  ожидаем OCS-ошибку, exit 1/2 по общему контракту», либо добавить в §3/§6 пункт проверить
  поведение на живом сервере для покинутой комнаты и зафиксировать наблюдение.

### 4. Гость: и комментарий формата `actorId`, и синтетическая строка в фикстуре — не проверены на этом эндпоинте

- **Цитата (§4/§6):** `ActorId string … // для guests — "guest::<anon-id>"`; «В фикстуру можно
  добавить участника-гостя (`participantType=4`, пустой `displayName`) — по полям формат
  идентичен (живая выборка гостей не содержала…)».
- **Что не так:** оба утверждения переносятся с чужого эндпоинта/документации: комментарий
  формата скопирован с `ReactionActor` reactions-API
  ([internal/client/reactions.go:20](file:///Users/stas/Projects/My/NCCliClient/internal/client/reactions.go)),
  а §3 честно признаёт, что живая выборка участников гостей не содержала и значения 4–6 — из
  документации. При этом проектный инвариант (CLAUDE.md): «Фикстуры `testdata/` обязаны
  отражать реальный формат каждого эндпоинта — самопальные объектные фикстуры однажды скрыли
  баг». Синтетическая строка гостя в фикстуре, объявленной «реального формата, снятой с живого»,
  закрепит непроверенное ожидание (в т.ч. пустой `displayName` и формат `actorId`) в тестах.
- **Что сделать:** пометить в §4/§6 формат гостевых полей как assumption (источник —
  reactions-эндпоинт + документация), либо вынести синтетического гостя в отдельную,
  явно помеченную синтетической фикстуру, и при первом удобном живом прогоне (комната с гостем)
  сверить фактические поля.

### 2. Кейс `data: null` не покрыт

- **Цитата (§4/§6):** «Пустой ответ сервера → пустой (non-nil) слайс»; тест-кейс только
  «пустой `data: []` → пустой non-nil слайс».
- **Что не так:** `ocs.data: null` доходит до Unmarshal (guard `len(data)>0` пропускает
  `RawMessage("null")` — прецедент явно разобран у `GetReactions`,
  [internal/client/reactions.go:32-35,46-50](file:///Users/stas/Projects/My/NCCliClient/internal/client/reactions.go)),
  и тогда слайс останется nil → `--json` напечатал бы `null`. Нормализация в §4 названа только
  для `SessionIds`; фраза «пустой ответ» двусмысленна (`[]` или `null`?).
- **Что сделать:** уточнить: «`data: []` ИЛИ `data: null` → non-nil пустой слайс», при желании —
  кейс в §6.

### 3. Не сказано, по чему сортируется «имя»

- **Цитата (§2/§5):** «сортировка: роль … → имя (case-insensitive)»; «`DisplayName`
  case-insensitive asc». Колонка ИМЯ при пустом `displayName` печатает fallback `actorId`.
- **Что не так:** двусмысленность: сортировать по сырому `DisplayName` (все безымянные гости

  `actorId`)? Две разумные реализации.
- **Что сделать:** одним предложением зафиксировать ключ сортировки (сырое поле или fallback).
