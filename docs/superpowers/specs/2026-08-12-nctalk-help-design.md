# Дизайн: `--help` для `nctalk`

Дата: 2026-08-12
Статус: одобрен дизайн, ожидает плана реализации
Связанные: [`2026-07-17-nctalk-cli-design.md`](./2026-07-17-nctalk-cli-design.md) — эталон контракта базового CLI (help в нём не описан — этот spec закрывает пробел).

## 1. Цель и контекст

В базовом `nctalk` (`cmd/nctalk` + `internal/cli`) **нет `--help`**. Флаг нигде не перехватывается и падает в роутер как обычный аргумент:

| Вызов сейчас | Вывод | exit |
|---|---|---|
| `nctalk --help` | `nctalk --help: ожидается verb (...)` | 1 |
| `nctalk` (без аргументов) | `nctalk: неизвестная команда; ожидается одна из: rooms, chat, reactions, search` | 1 |
| `nctalk rooms --help` | `nctalk rooms: неизвестный verb "--help"` | 1 |

Базовый CLI разбирается вручную по таблице `routes` (`internal/cli/cli.go`) без стандартного `flag`-пакета, поэтому автоматического help нет (в отличие от звонковых `nctalk-call`/`nctalk-talk`, где `flag.NewFlagSet` даёт `-h`/`--help` штатно). В контракте `2026-07-17-...-design.md` поведение help **не описано** — это пробел дизайна, а не баг.

**Цель:** добавить полноценный, детальный help в базовый `nctalk`, не меняя существующий парсинг флагов команд и не затрагивая звонковые бинарники.

### Out of scope (за рамками этого spec)

- Не генерируем help из структуры флагов автоматически (YAGNI — потянуло бы рефакторинг всех handler-ов). Тексты пишутся вручную.
- Не трогаем звонковые бинарники `nctalk-call`/`nctalk-talk`/`spike-check` — там `flag`-пакет, help уже работает.
- Не добавляем man-страницу, shell-completion, `--version` — отдельные фичи.
- Не меняем существующие флаги команд (`--name`, `--last`, фильтры `chat show` и т.д.) — их парсинг и инварианты (`2026-07-17-...-design.md` §8) остаются как есть.

## 2. Точки входа (что перехватывается)

Перехват происходит в `run()` (`cmd/nctalk/main.go`) **до** `config.Load()` и `cli.Run`/роутинга по `routes` (см. §5 — это требование без-кредового help). `--help`/`-h`/`help` распознаются специальным образом и не доходят ни до `config.Load`, ни до handler-ов.

| Вызов | Что показывает | Куда | exit |
|---|---|---|---|
| `nctalk --help` / `nctalk -h` / `nctalk help` | общий help (§3) | stdout | **0** |
| `nctalk help <resource>` (напр. `nctalk help rooms`) | help по ресурсу (список его verbs) | stdout | **0** |
| `nctalk help <resource> <verb>` (напр. `nctalk help chat show`) | детальный help по команде (§4) | stdout | **0** |
| `nctalk <resource> <verb> --help` (или `-h`) | детальный help по команде (§4) | stdout | **0** |
| `nctalk <resource> --help` (или `-h`) | help по ресурсу | stdout | **0** |
| `nctalk` (без аргументов) | общий help (§3) | **stderr** | **1** (ошибка использования) |
| `nctalk help nonsuch` (неизвестная команда) | сообщение «неизвестная команда» + подсказка `nctalk --help` | stderr | **1** |

Контракт exit-кодов (`2026-07-17-...-design.md` §7: `0` успех / `1` общая ошибка / `2` not found / `3` ambiguous) **расширяется** новыми случаями help и не нарушается:
- успешный help → `0` (частный случай «успех»);
- вызов без аргументов → `1` (ошибка использования, как и сегодня);
- `help <несуществующее>` → `1` (общая ошибка, согласовано с текущим «неизвестная команда → 1»).

### Правила разбора help-форм

- `--help` и `-h` — равнозначны, распознаются как флаги в любой позиции args. Сам факт их наличия = запрос help.
- `help` — только как **первое** слово (`args[0] == "help"`). Всё, что после него — путь к команде (`help`, `help rooms`, `help rooms list`).
- **Какой именно help** определяется путём команды, оставшимся после вырезания `--help`/`-h`/ведущего `help`:
  - путь пуст → общий help (§3);
  - путь = `<resource>` → help по ресурсу;
  - путь = `<resource> <verb>` → детальный help (§4);
  - путь = `<leaf-команда без verb-уровня>` (в MVP это `search` — special-case в `cli.go`, не входит в таблицу `routes`) → детальный help (§4) по этой leaf-команде.
  - Таким образом `nctalk rooms list --help`, `nctalk --help rooms list`, `nctalk help rooms list` — **все три** дают детальный help по `rooms list`; `nctalk search --help` и `nctalk help search` — детальный help по `search`. Позиция флага не влияет на результат.
- **Приоритет над выполнением:** если распознан запрос help, команда **не выполняется** (help «выигрывает»); сеть/клиент не затрагиваются.
- `--json` при запросе help **игнорируется** — help всегда текстовый, в человекочитаемом виде (вывод help не бывает JSON).
- **Путь команды** для help-запроса = первые **1-2 не-флаговых токена** из остатка args после вырезания `--help`/`-h`/ведущего `help`. Все `--*` (вместе со значениями по форме `--flag value`/`--flag=value`) при вычислении пути выкидываются; лишние не-флаговые токены сверх двух на класс help не влияют. Например, `chat show abc123 --help` → путь `chat show` (детальный help); `rooms list --nope --help` → путь `rooms list` (unknown-флаг `--nope` выкинут, показывается детальный help — **не** «неизвестная команда», т.к. help имеет приоритет над ошибкой парсинга handler-а).
- Если путь указывает на несуществующую команду (`nctalk help nosuch` с путём `nosuch` — нет такого resource; `nctalk rooms nosuch --help` с путём `rooms nosuch` — нет такого verb для `rooms`; и т.п.) → сообщение «неизвестная команда» + подсказка `nctalk --help`, exit `1`.
- **Порядок разбора args** в `run()` (см. §5) — строго такой, чтобы help-перехват шёл раньше `config.Load`/`extractJSON`/роутинга (и тем самым `args[0] == "help"` проверяется до `extractJSON`):
  1. Вырезаем из args все `--help`/`-h` (в любой позиции); если хотя бы одно было — запоминаем `helpRequested=true`.
  2. Если первый из оставшихся токенов — `help`, вырезаем его и тоже выставляем `helpRequested=true` (это единственная форма `help` как ведущего слова; `help` не в первой позиции help-запросом не является).
  3. Если `helpRequested` — вычисляем путь, вызываем `cli.HandleHelp(путь, deps)` и выходим с его exit-кодом; `config.Load`/`extractJSON`/роутинг **не выполняются** (поэтому help работает без `NEXTCLOUD_*` и `--json` молча игнорируется).
  4. Иначе — обычный flow: `config.Load` → `cli.Run` (внутри которого `extractJSON` и роутинг по `routes`); handler-ы никогда не видят `--help`/`-h`.

## 3. Формат: общий help (`nctalk --help`)

```
nctalk — тонкий CLI над Nextcloud Talk (Spreed)

Использование:
  nctalk <команда> [flags]
  nctalk <команда> --help    помощь по команде
  nctalk --help              эта справка

Команды:
  rooms list                список комнат
  rooms find <запрос>       найти комнату по фильтру
  rooms search <term>       поиск комнат на сервере
  chat show <room>          история чата комнаты
  chat send <room>          отправить сообщение (stdin или --file)
  reactions get <room> <id> реакции на сообщение
  search <term>             глобальный поиск по сообщениям

Глобальные флаги:
  --json                    вывод в JSON (в любой позиции)

Окружение:
  NEXTCLOUD_URL             адрес сервера (https://...)
  NEXTCLOUD_LOGIN           логин
  NEXTCLOUD_PASS            app-password (только env)
  NEXTCLOUD_TIMEOUT         таймаут HTTP (по умолчанию 30s)

Exit-коды: 0 — успех, 1 — общая ошибка/сеть/401/5xx,
           2 — не найдено, 3 — неоднозначное совпадение.
```

## 4. Формат: детальный help по команде (`nctalk <cmd> --help`)

Единый шаблон для всех 7 команд. Пример для `chat show`:

```
nctalk chat show — история чата комнаты

Использование:
  nctalk chat show <room> [flags]

<room> — token комнаты позиционно, либо --name для разрешения по имени.

Флаги:
  --name <имя>       разрешить комнату по имени (вместо token)
  --last N           количество сообщений (по умолчанию 20)
  --from <actorId>   только сообщения автора
  --since <время>    с момента времени (1h, 2d или ISO)
  --system           показывать system-сообщения (скрыты по умолчанию)
  --json             вывод в JSON

Примеры:
  nctalk chat show abc123 --last 50
  nctalk chat show --name "Команда" --since 1h
```

Help по ресурсу (`nctalk help rooms` / `nctalk rooms --help`) показывает заголовок ресурса + список его verbs с краткими описаниями + отсылку `nctalk rooms <verb> --help`.

### Канон текстов по командам

Тексты флагов обязаны совпадать с реальным парсингом в handler-ах. Сводка (источник — `internal/cli/handlers_*.go`):

| Команда | Флаги |
|---|---|
| `rooms list` | `--type <1\|2\|3>`, `--unread`, `--include-former` |
| `rooms find` | `--user <actorId>` |
| `rooms search <term>` | — (без флагов; `limit` фиксируется в `0`) |
| `chat show <room>` | `--name`, `--last N`, `--from`, `--since`, `--system` |
| `chat send <room>` | `--name`, `--reply-to`, `--reference-id`, `--silent`, `--file <путь>` (или stdin) |
| `reactions get <room> <messageId>` | `--name` |
| `search <term>` | `--from`, `--limit N`, `--all` |

Плюс глобальный `--json` (в любой позиции) у каждой команды.

## 5. Реализация (технические рамки)

- **Перехват help** — в `cmd/nctalk/main.go` функция `run`, **строго до `config.Load()`** (это безусловное требование §6: help должен работать без `NEXTCLOUD_*`). Сам разбор help-форм и тексты живут в `internal/cli` (отдельный файл `help.go`, экспортируемая функция вроде `cli.HandleHelp(args, deps) (handled bool, exit int)` для тестируемости); `run()` только решает «help-запрос или обычный flow» и в случае help вызывает `cli.HandleHelp` сразу, минуя `config.Load()`/`client.NewTalkClient`/`cli.Run`. Тем самым `nctalk --help` / `nctalk help ...` / `nctalk <cmd> --help` / `nctalk` (no-args, см. §2) не требуют кредов и не создают клиент.
- **Следствие для существующих тестов:** `TestRun_NoEnv_Returns1` в `cmd/nctalk/main_test.go` сегодня подаёт `nil` args и проверяет, что stderr содержит config-ошибку со словом «обязателен». После правки поведения `nctalk` без аргументов показывает общий help в stderr с exit 1 (§2), а не config-ошибку — тест нужно скорректировать: подавать args, реально доходящие до `config.Load()` (например `["rooms","list"]`), и проверять config-ошибку на этом пути.
- **Тексты help** — в одном месте, отдельный файл `internal/cli/help.go`. Все usage-строки — константы/структура, генерирующая вывод. Единый источник, чтобы не плодить копии.
- **Парсинг флагов команд не меняется.** Handler-ы остаются как есть; `--help`/`-h` вырезаются из args до того, как args дойдут до handler-а (аналогично `extractJSON`). Существующие инварианты (`2026-07-17-...-design.md` §6, §8) сохраняются.
- **Потоки:** успешный help пишет в `deps.Stdout`, ошибки/no-args — в `deps.Stderr` (тестируется через `bytes.Buffer`).
- **Изоляция от звонков:** изменения только в `internal/cli` + `cmd/nctalk`. Статический guard `TestCmdNctalkDoesNotDependOnPion` должен оставаться зелёным. Звонковые бинарники не трогаются.

## 6. Тестирование

- **Snapshot-тесты вывода** (в `internal/cli/help_test.go`): общий help и детальный help каждой из 7 команд содержат ожидаемые ключевые строки (команда, каждый её флаг, описание).
- **Exit-коды:** `--help`/`-h`/`help` → `0`; без аргументов → `1`; `help nonsuch` → `1`.
- **Потоки:** успешный help — в stdout, no-args — в stderr.
- **Без сети/кредов:** при запросе help клиент не создаётся/не вызывается (help работает без `NEXTCLOUD_*`).
- **Анти-рассинхрон (защита от устаревших текстов):** две независимых проверки на каждую команду, сведённые к одной декларации ожидаемых флагов (список флагов на команду — единый источник правды для обоих тестов):
  1. **help↔декларация:** тест сверяет, что help-текст команды упоминает ровно флаги из декларации (без лишних и без пропущенных);
  2. **декларация↔handler:** тест сверяет, что декларация совпадает с реальным парсингом handler-а — каждый заявленный флаг handler принимает (вызов с mock-клиентом и этим флагом не возвращает «неизвестный флаг»), а любой не-заявленный `--*` отвергается как «неизвестный флаг». Источник правды для поведения handler-а — сами handler-ы (`internal/cli/handlers_*.go`).
  Вместе это ловит оба класса дрейфа: «флаг есть в handler, но забыли в help» и «help упоминает флаг, которого handler не парсит» (второе — ровно тот баг, который этот обзор нашёл в §4 для `rooms find --include-former` и `rooms search --limit`; без проверки 2 декларация могла бы быть источником той же ошибки).
- Изоляционный guard `TestCmdNctalkDoesNotDependOnPion` остаётся зелёным.

## 7. Будущее (явно за рамками)

- `--version` / сборка из `debug.ReadBuildInfo`.
- Авто-генерация help из декларативной схемы флагов (если handler-и когда-нибудь мигрируют на `flag.FlagSet`).
- Shell-completion (bash/zsh/fish).
- Help для звонковых бинарников дополнительно унифицировать (сейчас — стандартный `flag`-вывод).
