## Корректность (баги)

### [MAJOR] Пагинация `GetChat` игнорирует документированный `X-Chat-Last-Given` и опирается на порядок «от новых к старым»
Файл: `internal/client/chat.go:92` (и `:60`–`110`, ранний стоп `:77`–`89`)
Проблема: Следующая страница считается как `lastKnown = page[len(page)-1].Id` — id последнего элемента массива. Но официальная документация Nextcloud Talk явно указывает: offset для следующей страницы нужно брать из **response-заголовка `X-Chat-Last-Given`**, а не из тела. Если сервер отдаёт пачку истории в хронологическом порядке (старые→новые, что типично для Talk), то `page[len-1]` — самое свежее в пачке, и следующий запрос `lastKnownMessageId=<новейшее>` запросит «старее свежего» → пересечение/повторы, пагинация назад не двигается. Ранний стоп по `StopBeforeTs` (`:77`–`89`) делает то же допущение (ищет первое «слишком старое» и режет `page[:cut]`) — при ascending-порядке он обнулит результат. Мультистраничная пагинация **не верифицирована** против реального сервера: интеграционный `TestIntegration_GetChat` гоняет только `Limit:5` (одна страница, 200), а `TestGetChat_TwoPages_*` — на самопальной фикстуре, совпадающей с допущением кода.
Предложение: Возвращать `resp.Header` из транспорта, читать `X-Chat-Last-Given` и использовать его как `lastKnown` для следующей страницы; стоп — когда заголовок пуст или не изменился. Заодно это снимает зависимость от порядка и хак с `len(page) < chatPageSize`.

### [MAJOR] HTTP `304 Not Modified` не обрабатывается → decode-ошибка вместо чистого конца истории
Файл: `internal/client/chat.go:181` (`doOCSGet`), `internal/client/client.go:152` (`doOCS`)
Проблема: Документация chat-эндпоинта: сервер возвращает `304 Not Modified` «when there were no older/newer messages» — в теле при `lookIntoFuture=0` это означает «достигли начала чата» (а для пустого чата — возможно и на первом запросе). Тело у 304 пустое → `json.NewDecoder(resp.Body).Decode(&env)` падает с `EOF` → `GetChat` возвращает ошибку «не удалось декодировать OCS-ответ» вместо остановки. Любой `chat show`, дошедший до начала истории (или `--since`/`--from`, выгребающие несколько страниц до дна), на боевом сервере упадёт. Тесты это не ловят (фикстуры всегда отдают 200 + `[]`).
Предложение: До декодирования проверять `resp.StatusCode`: `304` (и `204`) трактовать как пустую страницу → чистый стоп пагинации. Заодно включить статус в текст decode-ошибки для не-OCS-ответов.

### [MAJOR] `GetReactions` при `ocs.data: null` возвращает nil-мапу → `--json` печатает `null` вместо `{}`
Файл: `internal/client/reactions.go:42`–`46`
Проблема: `json.Unmarshal([]byte("null"), &out)` обнуляет заранее сделанную `make(...)` мапу в **nil** (guard `len(env.OCS.Data) > 0` при этом пропускает, т.к. `json.RawMessage("null")` имеет len 4). Итог: `GetReactions` возвращает `nil, nil`, контракт «non-nil пустая map» нарушен, `render.ReactionsJSON(nil)` маршалит `null` (а не `{}`). Актуальный Nextcloud сегодня отдаёт `{}` для пустых реакций, поэтому в проде пока не стреляет — но это реальный дефект с ложной гарантией в комментарии.
Предложение: После `doOCS` сделать как в `getChatPage`: `if out == nil { out = map[string][]ReactionActor{} }` (или инициализировать после анмаршала).

### [MINOR] `chat send` не триммит trailing-newline из stdin/файла
Файл: `internal/cli/handlers_chat.go:376`, `:381`, `:404`
Проблема: `io.ReadAll(stdin)` / `os.ReadFile` оставляют `\n` как есть. `echo "hi" | nctalk chat send room` отправит `"hi\n"`; сервер сохранит с переводом строки.
Предложение: Срезать один завершающий `\n` (`\r\n`), либо задокументировать «тело как есть».

### [MINOR] `--reply-to` / `<messageId>` принимают неположительные значения без guard
Файл: `internal/cli/handlers_chat.go:354`, `internal/cli/handlers_reactions.go:98`
Проблема: `strconv.Atoi` пропускает `0` и отрицательные → лишний сетевой запрос и серверный 4xx вместо понятной клиентской ошибки.
Предложение: Отсекать `<= 0` до сетевого вызова.

### [MINOR] Траверсал пути / двойное кодирование через `path.Join` над пользовательским token
Файл: `internal/client/client.go:114`, `internal/client/chat.go:146`, `internal/client/search.go:121`
Проблема: `path.Join(baseURL.Path, p)` вызывает `Clean`: позиционный token `".."` схлопнет родительский сегмент (запрос уйдёт на вышестоящий путь). Токены с `%2F` (после `PathEscape`) `url.String()` до кодирует в `%252F`. Токены серверные и обычно безопасны, но positional приходит от пользователя.
Предложение: Использовать `url.JoinPath` (Go 1.19+, в `go.mod` 1.21) вместо ручного `path.Join`, и/или валидировать token по safe-charset.

### [MINOR] `setReadMarker` по умолчанию = 1 → `chat show` молча помечает комнату прочитанной
Файл: `internal/cli/handlers_chat.go` (`getChatPage`, `internal/client/chat.go:116`–`124`)
Проблема: По документации Talk `setReadMarker` дефолт = 1. Читающий `chat show` имеет побочный эффект — сбрасывает unread. Для CLI-«подглянуть» обычно нежелательно.
Предложение: Явно передавать `setReadMarker=0` (если спека не требует иного).

## Упрощения (DRY)

### [MAJOR] Три копии OCS-транспорта: `doOCS` / `doOCSGet` / `doSearchOCSGet`
Файл: `internal/client/client.go:110`, `internal/client/chat.go:144`, `internal/client/search.go:117`
Проблема: ~40 строк почти идентичного кода (сборка URL, сборка `Authorization` на каждый запрос, заголовки `OCS-APIRequest`/`Accept`, двухфазный decode, `sanitizeErr`, закрытие `Body`) размножены ×3. Рассинхрон-риск: любое изменение redact/контракта ошибок/заголовков нужно вносить в трёх местах; `doOCS` принципиально не умеет в `RawQuery`, что и породило клоны.
Предложение: Расширить сигнатуру `doOCS(ctx, method, path, query url.Values, body, mutate, out)` и удалить `doOCSGet`/`doSearchOCSGet`. Все пути уже разложены по константам — конфликт при слиянии минимален.

### [MINOR] Дублированный `parseRelative` (`render` vs `cli`)
Файл: `internal/render/parse_since.go:54`, `internal/cli/handlers_chat.go:243`
Проблема: `parseRelativeAt` в cli копирует `parseRelative` из render, чтобы прокинуть `deps.Now`. Если набор суффиксов (s/m/h/d) изменится в одном месте, второе рассинхронизируется.
Предложение: Экспортировать `render.ParseRelativeAt(s, now)` и звать его из обоих мест; `ParseSince` сделать обёрткой с `time.Now`.

### [MINOR] `SubstituteParams` для `type=file` теряет ссылку
Файл: `internal/render/params.go:39`, `internal/render/render.go:70`
Проблема: Комментарий обещает «ссылка прикладывается в render-слое», но `MessagesTable` печатает `Message` как есть — `MsgParam.Link` нигде не выводится. В текстовом режиме файловый плейсхолдер превращается только в имя без ссылки.
Предложение: В `MessagesTable` после подстановки дозакладывать ссылку для файловых параметров (или явно зафиксировать в спеке, что MVP ссылку не показывает).

## Эффективность

### [MINOR] Дефолтный `chat show` (limit=20) тянет со сервера 200 сообщений и выкидывает 180
Файл: `internal/client/chat.go:29`, `internal/cli/handlers_chat.go:147`–`153`
Проблема: Серверный `limit` всегда захардкожен в `chatPageSize=200`, хотя Talk API принимает 1..200. В самом частом сценарии (`chat show room`, limit=20) по сети идёт в 10 раз больше данных, чем нужно.
Предложение: Передавать серверу `limit=min(opts.Limit, 200)` (при `opts.Limit>0`), оставив клиентский потолок как страховку.

### [MINOR] Эвристика предупреждения `sampleLen == 200` ложноположительна при `--last 200`
Файл: `internal/cli/handlers_chat.go:195`
Проблема: При явном `--last 200` и пустом фильтре предупреждение «выборка ограничена 200» сработает, даже если более старых сообщений нет.
Предложение: Гнать предупреждение только когда `opts.Limit` НЕ продиктован `--last` (т.е. когда реально упёрлись в cap), либо сигнализировать «есть ещё» через `X-Chat-Last-Given`.

### [MINOR] `--last N` после клиентского фильтра system-сообщений возвращает меньше N (или 0)
Файл: `internal/cli/handlers_chat.go:176`–`190`
Проблема: `--last 50` сначала тянет 50 «сырых» (с system), затем фильтрует локально — пользователь видит <50. Принято спекой (клиентский фильтр), но неожиданно; refill-пагинации нет. Фиксируется как ограничение MVP.

## Замечания вне категорий (робастность)

### [MINOR] `doOCS`/`doOCSGet` игнорируют HTTP-статус; не-OCS тело даёт непрозрачную decode-ошибку
Файл: `internal/client/client.go:152`, `internal/client/chat.go:181`, `internal/client/search.go:155`
Проблема: Если reverse-proxy вернёт HTML (5xx или 200 login-page), `json.Decode` падает с `invalid character '<'`, а HTTP-статус теряется — отладка боли. Связано с кейсами 304 и network/4xx/5xx.
Предложение: При ошибке decode включать `resp.StatusCode` (и, опционально, `Content-Type`) в текст ошибки.

### [MINOR] `sameHostRedirectPolicy` игнорирует схему — возможен даунгрейд https→http с утечкой Basic-auth
Файл: `internal/client/client.go:87`–`96`
Проблема: Политика сравнивает только `Host`. Same-host редирект `https://nc` → `http://nc` (через кривой прокси) разрешается, и `Authorization` (с паролем) уходит в открытом виде. Спека говорит «same-host follows», но про схему умалчивает.
Предложение: Дополнительно требовать `req.URL.Scheme == via[last].URL.Scheme` (минимум — блокировать даунгрейд с https на http).

## Сводка

Всего замечаний: **15** (blocker **0** / major **4** / minor **11**).

Качество кода **высокое**: чистая слоистая архитектура (config → client → cli → render), продуманные контракты ошибок и exit-кодов, красные тесты на redact/redirect/пагинацию, аккуратная работа с `resp.Body.Close` и `sanitizeErr`. Утечек пароля в URL/ошибках/логах не найдено.

Слабое место одно — **пагинация `chat show`**: реализована и протестирована только против самопальных фикстур и расходится с документированным контрактом Talk (заголовок `X-Chat-Last-Given`, обработка `304`, неявное допущение о порядке сообщений). Дефолтный одностраничный путь работает, но мультистраничный/до-дна на боевом сервере, скорее всего, либо зациклится/повторится, либо упадёт с decode-ошибкой на 304. Рекомендация: до релиза провести интеграционный тест `GetChat` с `Limit>200` (до начала истории) на реальном сервере — это вскроет обе major-проблемы одновременно. Тривиальный рефакторинг транспорта (merge трёх `doOCS*`) заодно снимет рассинхрон-риск.
