## 1. Корректность

**1.1 (medium) Молчаливый `id=0` при неожиданном формате ответа** — `internal/client/chat.go`
`EditMessage`: если сервер вернёт 200/202 без `parent` (или с `parent.id=0`), метод вернёт
`0, nil` → CLI напечатает `0` / `{"id":0}` с **exit 0**. Спека прямо говорит, что формат
PUT-ответа «не проверен на живом API» и фиксируется тестами — но это проверяется только
integration-тестом под флагом. Unit-уровня защиты от drift формата нет: продакшен-пользователь
получит бесшумный успех с фиктивным id. Рекомендация: guard
`out.Parent.Id <= 0 → error "client: EditMessage: неожиданный формат ответа (нет parent.id)"`.
(Замечание: у `SendMessage` та же слабость — общее улучшение, но у edit риск выше, формат
экзотичнее.)

**1.2 (info) `strconv.Atoi` принимает `+2927`** → messageId спарсится, отправится
`PUT .../2927`. Безвредно; для строгого decimal нужна ручная проверка isdigit
(`ParseInt(s, 10, 0)` тоже принимает `+`). Не блокер.

## 2. Упрощения

**2.1 (medium) Дублирование блока чтения тела, ~30 строк** — `internal/cli/handlers_chat.go`
(send-блок vs новый edit-блок): `--file`/stdin-fallback/`io.ReadAll`/трим ровно одного
`\r\n`/`\n`/проверка пустоты — скопированы дословно, отличается только префикс ошибки
(`chat send:` / `chat edit:`). Третья копия (если появится `chat delete`) почти неизбежна.
Естественный extraction: `readMessageBody(deps Deps, fileFlag, cmd string) (string, ExitError)`.
Тесты уже покрывают обе копии одинаковыми кейсами — рефакторинг безопасен. Не блокер
слияния, но лучше сделать сейчас, пока кейсов мало.

**2.2 (info) Дублирование тест-хелпера** — `chatEditServer`/`chatEditReqLog` в
`internal/client/chat_test.go` повторяют паттерн логирующего httptest-сервера из соседних
тест-файлов (reactions/search). Общий `reqLogServer`-хелпер сократил бы ~30 строк. Косметика.

## 3. Эффективность

Существенных проблем нет: один запрос, `json.Marshal` одного поля, `PathEscape` только
token (messageId через `Itoa` — корректно и безопасно), guard-ы отсекают сеть.
Пагинации/ретраев тут не нужно.

## 4. Расхождения со спекой (не баги кода)

**4.1 Фикстура в корневом `testdata/`, а спека §6 говорит `internal/client/testdata/`** —
код **прав**, спека нет: все клиентские фикстуры проекта (rooms/reactions/search) лежат в
корневом `testdata/`, тесты читают `../../testdata/`. Стоит поправить текст спеки, чтобы
следующий исполнитель по §6 не «перенёс» фикстуру.

**4.2 Спека §5 vs UX** — порядок «чтение тела ДО парсинга messageId» (реализовано как в
спеке) означает: `nctalk chat edit TOK abc` на интерактивном TTY сначала зависнет на
stdin, и только после ввода тела скажет «невалидный messageId». Парсинг messageId первым
был бы дружелюбнее и тоже «до сети». Спека сознательно так решила — оставлено как есть,
отмечено для будущей спеки `chat delete`.
